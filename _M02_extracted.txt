2.  DASAR TEORI (RINGKAS) 
Linux sebagai substrat kerja DevOps. Dalam dunia industri perangkat lunak, kata substrat 
mengacu pada lapisan dasar tempat segala sesuatu berpijak dan beroperasi. Sepanjang semester 
ini, berbagai toolchain modern seperti Docker, Kubernetes, Terraform, Ansible, hingga runner 
CI/CD akan digunakan secara intensif. Perlu disadari bahwa hampir seluruh perkakas/tools 
tersebut dirancang untuk berjalan secara native di atas kernel Linux.  
Di lingkungan produksi (production), pengelolaan infrastruktur tidak dilakukan melalui antarmuka 
grafis (GUI) atau klik manual, melainkan melalui antarmuka baris perintah (Command Line 
Interface / CLI) dan skrip otomasi. Oleh karena itu, penguasaan terhadap mekanisme dasar Linux 
bukan sekadar materi pelengkap, melainkan prasyarat mutlak sebelum melangkah ke otomasi 
tingkat lanjut dan implementasi keamanan siber terintegrasi (DevSecOps). 
Fondasi interaksi di Linux berdiri di atas dua pilar utama: 
• Filesystem Hierarchy Standard (FHS). 
Berbeda dengan Windows yang menggunakan drive letter (seperti C:\ atau D:\), Linux menata 
seluruh sistem berkasnya dalam satu pohon hierarki tunggal yang berakar pada direktori root 
(/). Aturan penempatan ini distandarisasi  lewat Filesystem Hierarchy Standard (FHS).  
Tujuan FHS adalah menjaga konsistensi: program apa pun dan engineer mana pun dapat 
memprediksi lokasi file tanpa harus menebak-nebak.

• Mekanisme perizinan dan isolasi akses (Ownership & Permissions). 
Linux dirancang sejak awal sebagai sistem operasi multi -user. Untuk melindungi integritas 
data, setiap berkas dan direktori dilindungi oleh matriks perizinan yang ketat.  
1. Pembagian Entitas Pengguna 
- User (u): Akun pemilik sah berkas (file owner). 
- Group (g): Kelompok pengguna yang memiliki hak kerja sama pada berkas tersebut. 
- Other (o): Seluruh pengguna lain di luar pemilik dan anggota grup. 
2. Tipe Izin Akses 
- Read (r - nilai 4): Izin untuk membuka dan membaca isi berkas atau melihat daftar isi 
folder. 
- Write (w - nilai 2): Izin untuk memodifikasi isi berkas, membuat berkas baru, atau 
menghapusnya. 
- Execute (x - nilai 1): Izin untuk mengeksekusi berkas sebagai program/skrip atau 
memasuki direktori. 
Dari mekanisme hak akses di atas, lahirlah prinsip dasar keamanan sistem yang disebut 
Principle of Least Privilege: 
 
"Setiap proses, pengguna, atau layanan hanya boleh diberikan izin akses seminimal 
mungkin yang diperlukan untuk menyelesaikan pekerjaannya." 
 
Di lingkungan kerja DevOps, ada dua kebiasaan buruk yang sering dianggap "solusi cepat" 
saat menghadapi eror, padahal berakibat fatal bagi keamanan sistem: 
 
1. Memberikan Hak Akses Penuh: chmod 777 
- Masalah: Angka 777 berarti memberikan akses rwx (baca, tulis, eksekusi) kepada 
User, Group, dan Other sekaligus. 
 
- Risiko: Perintah ini melanggar prinsip least privilege secara total. Jika sebuah folder 
aplikasi diberi hak 777, siapa pun termasuk script berbahaya yang berhasil masuk ke 
server bisa mengubah kode sumber aplikasi, membaca file credential (seperti token 
API atau password database), hingga menyisipkan backdoor. 
 
2. Menjalankan Aplikasi dan Kontainer sebagai root 
- Masalah: Akun root adalah superuser yang memiliki kendali tanpa batas atas seluruh 
aspek sistem operasi. 
 
- Risiko: Jika sebuah aplikasi web atau kontainer Docker dijalankan sebagai root, lalu 
aplikasi tersebut memiliki celah keamanan (misalnya Remote Code Execution),

Filosofi Unix: Do One Thing and Do It Well 
Salah satu kekuatan terbesar antarmuka CLI ( Command Line Interface ) di Linux bukanlah 
keberadaan satu aplikasi monolitik raksasa yang serba bisa. Justru sebaliknya, ekosistem Unix 
menganut filosofi: buat program-program kecil yang masing-masing hanya mengerjakan satu tugas 
spesifik dengan sempurna.  
Pipe dan Redirection: Perekat Aliran Data (Data Stream) 
Agar program-program kecil tersebut dapat saling terhubung, Linux menyediakan operator aliran 
data:  
1. Pipe (|) 
Menyambungkan keluaran ( standard output / stdout) dari program pertama langsung 
menjadi masukan (standard input / stdin) bagi program berikutnya secara real-time.  
2. Redirection (>, >>) 
o >: Menuliskan output ke dalam sebuah berkas (menimpa/mengganti isi berkas 
yang lama). 
o >>: Menambahkan ( append) output ke baris paling bawah berkas tanpa 
menghapus data lama. 
3. Stream Merging (2>&1) 
Mengarahkan saluran eror ( standard error / stderr / file descriptor 2) ke saluran output 
normal (stdout / file descriptor 1). Di dunia DevOps, operator ini sangat vital saat membuat 
skrip build agar pesan eror ikut terekam ke dalam berkas log atau sistem monitoring.  
Analitik Log Tradisional: "Mesin Analitik" Pertama Sebelum Era Modern . Jauh sebelum kita 
menggunakan dashboard visual seperti Prometheus dan Grafana (yang akan dipelajari pada 
pekan ke-14), seorang engineer mengandalkan kombinasi perkakas CLI untuk membedah traffic 
dan insiden: 
# Contoh skrip investigasi log web server: 
cat /var/log/nginx/access.log | grep " 500 " | awk '{print $1}' | sort | 
uniq -c | sort -nr 
Bagaimana data mengalir: 
- grep: Menyaring hanya baris log yang mengandung kode eror HTTP 500.    
- awk: Memilih dan mengambil kolom tertentu saja (misalnya alamat IP klien).    
- sort & uniq -c: Mengurutkan lalu mengagregasi/menghitung frekuensi kemunculan tiap IP 
secara otomatis.    
- sort -nr: Mengurutkan IP dari yang paling sering memicu eror ke yang paling sedikit. 
 
Kombinasi sederhana ini pada dasarnya adalah fungsi agregasi analitik yang sangat cepat untuk 
troubleshooting langsung di server target. 
 
Kontrak Exit Code: Fondasi Otomasi Pipeline CI/CD. Di dalam sistem operasi Linux, setiap kali 
sebuah program, skrip, atau perintah selesai dijalankan, proses tersebut secara wajib mengirimkan 
sinyal status yang disebut Exit Code (atau return code): 
- Nilai 0: Menandakan program berjalan sukses tanpa kendala.    
- Nilai selain 0 (1 s.d. 255): Menandakan terjadi kegagalan (error).

Hubungan Exit Code dengan CI/CD Runner . Runner pada platform CI/CD (seperti GitHub 
Actions atau GitLab CI) tidak "melihat" tampilan visual , mereka membaca exit code dari setiap 
command yang dieksekusi di dalam skrip pipeline. 
 
- Jika perintah unit test mengembalikan  0, runner menganggap tahap tersebut lulus (hijau) 
dan melanjutkan ke tahap deployment.    
- Jika unit test gagal, proses mengembalikan kode non -nol (misalnya 1), sehingga runner 
langsung menghentikan pipeline (merah) agar kode yang rusak tidak terdorong ke server 
produksi. 
 
Peringatan Kritis (DevOps Anti -Pattern): Membutakan Pipelin e. Jika seorang engineer 
membuat skrip otomasi yang secara tidak sengaja menelan eror (misalnya menambahkan || true 
atau memaksa baris terakhir skrip dengan exit 0), skrip tersebut akan selalu mengembalikan nilai 
0. Akibatnya, pipeline CI/CD menjadi buta  (tidak tahu mana yang gagal) . Runner akan 
menganggap semua tahapan sukses meski tes unit gagal atau proses kompilasi aplikasi rusak, 
dan kode berbahaya tersebut tetap meluncur ke lingkungan production. 
 
Shell script sebagai bentuk paling awal Infrastructure as Code. Sebuah prosedur manual yang 
ditulis dalam dokumen akan cepat basi, tetapi prosedur yang ditulis sebagai skrip dapat diversikan, 
ditinjau melalui pull request, diuji, dan dijalankan ulang oleh siapa pun dengan hasil yang sama. 
Agar layak disebut demikian, skrip harus memenuhi beberapa syarat: bersifat idempotent (aman 
dijalankan berulang), memuat penjagaan galat (set -euo pipefail dan trap), memisahkan fungsi 
yang dipakai bersama ke dalam pustaka, mencatat aktivitas melalui logging terstruktur, serta lolos 
analisis statis. Pada sisi operasional, systemd mengelola siklus hidup layanan dan journald 
mengumpulkan lognya, sehingga systemctl dan journalctl menjadi dua perintah pertama yang 
dijalankan saat sebuah layanan bermasalah. Semua praktik ini merupakan versi manual dari apa 
yang kelak diotomasi oleh Dockerfile pada minggu ke -6 dan oleh Ansible atau Terraform pada 
minggu ke-13.

⚠  PERINGATAN KEAMANAN & KESELAMATAN KERJA (WAJIB DIBACA) 
1.  Perintah penghapusan rekursif adalah risiko tertinggi pada praktikum ini. Selalu jalankan ls 
terhadap sebuah path sebelum menjalankan rm terhadap path yang sama. Satu spasi salah ketik 
pada rm -rf dapat menghapus seluruh direktori home Anda tanpa konfirmasi dan tanpa recycle bin. 
2.  Jangan pernah menjalankan chmod atau chown secara rekursif pada direktori sistem (/, /etc, /usr, 
/var). Tindakan tersebut dapat membuat sistem gagal boot. Batasi seluruh perubahan izin hanya 
pada ~/praktikum-devops. 
3.  Gunakan SIGTERM (kill -TERM atau kill tanpa opsi) sebelum SIGKILL (kill -9). SIGKILL tidak 
memberi kesempatan aplikasi menutup koneksi dan menyimpan data, sehingga berpotensi merusak 
berkas. 
4.  Dilarang menghentikan proses milik sistem atau pengguna lain. Pastikan PID yang Anda hentikan 
benar-benar milik proses Anda sendiri; verifikasi dengan pgrep -af sebelum mengirim sinyal. Jangan 
pernah mengirim sinyal ke PID 1. 
5.  Berkas log dapat memuat data sensitif (alamat IP, token pada query string, identitas pengguna). 
Log latihan pada praktikum ini bersifat sintetis; log produksi tidak boleh diunggah ke repository atau 
dibagikan ke luar kelas. 
6.  Tetap berlaku dari Minggu 1: dilarang chmod 777, dilarang commit kredensial, dan gunakan sudo 
hanya untuk instalasi paket.

disk_usage_pct() { df -P / | awk 'NR==2 { gsub("%","",$5); print $5 }'; } 
mem_used_pct()   { free | awk '/^Mem:/ { printf "%.0f", $3/$2*100 }'; } 
proc_count()     { ps -e --no-headers | wc -l; } 
  
main() { 
  while getopts ":d:jh" opt; do 
    case "$opt" in 
      d)  THRESHOLD_DISK="$OPTARG" ;; 
      j)  FORMAT="json" ;; 
      h)  usage; exit 0 ;; 
      \?) usage >&2; die "opsi tidak dikenal: -$OPTARG" ;; 
      :)  die "opsi -$OPTARG membutuhkan argumen" ;; 
    esac 
  done 
  
  [[ "$THRESHOLD_DISK" =~ ^[0-9]+$ ]] || die "ambang disk harus berupa angka" 
  
  local disk mem procs status 
  disk="$(disk_usage_pct)" 
  mem="$(mem_used_pct)" 
  procs="$(proc_count)" 
  status="OK" 
  (( disk >= THRESHOLD_DISK )) && status="PERINGATAN" 
  
  if [[ "$FORMAT" == "json" ]]; then 
    printf '{"host":"%s","disk_pct":%s,"mem_pct":%s,"proc":%s,"status":"%s"}\n' \ 
      "$(hostname)" "$disk" "$mem" "$procs" "$status" 
  else 
    printf '%-20s : %s\n'   'Host'             "$(hostname)" 
    printf '%-20s : %s%%\n' 'Pemakaian disk'   "$disk" 
    printf '%-20s : %s%%\n' 'Pemakaian memori' "$mem" 
    printf '%-20s : %s\n'   'Jumlah proses'    "$procs" 
    printf '%-20s : %s\n'   'Status'           "$status" 
  fi 
  
  [[ "$status" == "OK" ]] || return 2 
} 
  
main "$@" 
EOF

4.  TUGAS & EVALUASI 
4.1  Pertanyaan Analisis 
Jawablah pada laporan praktikum secara argumentatif dengan merujuk pada keluaran perintah 
yang Anda peroleh sendiri. Sertakan potongan keluaran terminal sebagai bukti pendukung. 
1. Batas kemampuan set -e. Skrip Anda telah memuat set -euo pipefail, namun mekanisme ini 
tidak menghentikan eksekusi pada semua kondisi. Jelaskan minimal dua situasi di mana 
perintah yang gagal tidak menghentikan skrip (misalnya di dalam kondisi if, di sisi kiri operator 
||, atau pada command substitution), lalu usulkan cara penanganan yang tepat untuk masing-
masing situasi. 
2. Agregat yang menyesatkan. Berdasarkan hasil JOB 2, laporkan angka proksi Change 
Failure Rate Anda. Kemudian jelaskan mengapa satu angka agregat dapat menyesatkan tim 
operasional, dengan merujuk pada sebaran kegagalan per endpoint yang Anda temukan. 
Rumuskan satu metrik tambahan yang lebih berguna untuk menentukan prioritas perbaikan. 
3. CLI versus GUI. Jelaskan mengapa antarmuka baris perintah menjadi prasyarat otomasi 
dengan meninjau tiga sifat: reproducibility, auditability, dan kemampuan disimpan pada 
version control. Selanjutnya, sebutkan satu situasi konkret di mana antarmuka grafis tetap 
merupakan pilihan yang lebih tepat, beserta alasannya. 
4. Least privilege pada otomasi. Seorang rekan menyarankan agar setup.sh dijalankan 
dengan sudo dan seluruh direktori aplikasi diberi izin 777 supaya tidak pernah muncul galat 
Permission denied. Analisis risiko konkret dari saran tersebut, lalu usulkan dua mekanisme 
pengganti yang tetap menyelesaikan masalah aslinya tanpa menaikkan hak akses. 
5. Idempotensi. Jalankan sysreport.sh dan setup.sh masing -masing tiga kali berturut -turut. 
Tentukan skrip mana yang bersifat idempotent dan mana yang tidak, disertai bukti keluaran. 
Jelaskan mengapa sifat ini menjadi syarat mutlak ketika konsep Infrastructure as Code 
diperkenalkan pada minggu ke-12.
