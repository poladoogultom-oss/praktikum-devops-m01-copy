2.  DASAR TEORI (RINGKAS) 
Cara Git Bekerja: Snapshot, Bukan Selisih . Git tidak menyimpan “daftar perubahan” tiap file 
seperti sistem version control lama (misalnya SVN atau CVS). Setiap kali kamu commit, Git 
menyimpan snapshot utuh dari kondisi proyek saat itu. 
Kalau ada file yang tidak berubah, Git tidak menyalin ulang isi file tersebut. Git hanya membuat 
referensi ke objek yang sudah ada. Ini membuat Git sangat efisien, terutama untuk proyek besar 
dengan banyak file. 
Tiga Jenis Objek di Git. Semua data di Git dibangun dari tiga jenis objek. Setiap objek diidentifikasi 
oleh hash (SHA-1) dari isinya, jadi kalau isi berubah, hash-nya juga berubah. 
Objek Fungsi 
blob Menyimpan isi file (konten mentah, tanpa nama file atau path). 
tree Menyimpan struktur folder: daftar nama file, tipe file, dan pointer ke blob atau tree 
lain. 
commit Menyimpan pointer ke tree utama, pointer ke commit induk (parent), info penulis, 
waktu, dan pesan commit. 
Karena setiap commit menunjuk ke commit induknya, riwayat Git membentuk struktur seperti 
pohon yang disebut directed acyclic graph (DAG). Tidak ada loop, dan setiap commit punya jalur 
unik ke commit pertama (root). 
Dua Konsekuensi Penting 
Desain ini punya dua dampak praktis yang sangat relevan untuk DevSecOps dan GitOps: 
1. Integritas Terjamin 
Kalau satu byte saja di file lama berubah: 
• Hash blob berubah 
• Hash tree yang merujuk ke blob itu ikut berubah 
• Hash commit yang merujuk ke tree itu juga berubah 
• Semua commit setelahnya ikut berubah hash-nya

Kenapa staging area penting 
Tanpa staging, Git hanya akan menyimpan “semua yang berubah”. Dengan staging, kamu bisa 
menyusun commit atomik: satu commit, satu perubahan logis. 
Commit yang kecil dan fokus punya dua manfaat operasional: 
• Gagal dan ingin dibatalkan: git revert hanya membatalkan satu perubahan, tanpa menyeret 
perubahan lain. 
• Ada bug yang muncul entah dari commit mana: git bisect lebih cepat menemukan 
penyebabnya karena setiap commit punya satu perubahan yang jelas. 
Ukuran commit jadi bukan soal kerapian saja. Commit yang kecil mempercepat pencarian dan 
pemulihan, jadi berdampak langsung ke Mean Time to Restore , salah satu metrik DORA di 
Minggu 1

a. git restore: Membuang Editan Lokal yang Belum Di-commit 
• Fungsi: Mengembalikan berkas di working directory ke kondisi terakhir saat commit. 
• Kapan dipakai: Anda sedang mencoba-coba menulis kode di laptop, hasilnya berantakan, 
dan Anda ingin menghapus semua eksperimen itu agar file kembali bersih seperti semula. 
Perubahan yang dibuang ini langsung hilang dan tidak masuk riwayat. 
b. git commit –amend: Mengganti Commit Terakhir 
• Fungsi: Menimpa atau merevisi satu commit paling ujung. 
• Kapan dipakai:  Anda baru saja melakukan commit, lalu sadar ada typo pada pesan 
commit, atau lupa menaruh satu file konfigurasi ke staging area . Daripada membuat 
commit baru bertuliskan "oops, ketinggalan satu file", Anda cukup menjalankan --amend 
untuk menggabungkannya ke commit terakhir. 
c. git reset: Mesin Waktu Lokal (3 Tingkat Kedalaman)

Bagaimana jika Anda tidak sengaja menjalankan git reset --hard dan mengira pekerjaan Anda 
hilang selamanya? Di sinilah peran git reflog (Reference Logs). 
• Cara Kerja:  reflog adalah mekanisme internal Git yang mencatat setiap pergerakan 
penunjuk HEAD di laptop Anda, mulai dari perpindahan branch, operasi checkout, hingga 
reset. Catatan ini disimpan di penyimpanan lokal selama kurang lebih 90 hari. 
• Fungsi Penyelamat: Selama kode tersebut sempat di -commit, commit hash-nya akan 
tercatat di reflog . Anda cukup menjalankan git reflog, mencari hash sesaat sebelum 
kecelakaan terjadi, lalu mengembalikannya dengan git reset --hard <commit_hash_reflog>. 
 
Meski Git memiliki fitur pemulihan seperti reflog, ada dua batasan mutlak yang wajib dipahami oleh 
setiap engineer: 
 
1. Reflog Tidak Menyelamatkan File yang Belum Pernah Di-commit 
Git hanya bisa melacak apa yang pernah Anda serahkan ke dalam database-nya. Jika 
Anda mengedit file di working directory, tidak pernah menjalankan git commit, lalu tidak 
sengaja mengeksekusi git restore . atau git reset --hard, perubahan tersebut hilang 
permanen tanpa bisa dipulihkan.  
 
2. Aspek DevSecOps: Sekali Kredensial Ter-commit, Sistem Dianggap Bocor! 
Sering terjadi pemula tidak sengaja meng -commit file berisi token API, private key, atau 
password database, lalu buru -buru menghapus file tersebut di commit berikutnya. 
 
• Fakta Keamanan: Menghapus file di commit terbaru tidak menghapus file tersebut dari 
riwayat Git. Siapa pun yang mengunduh repository masih bisa mengecek riwayat lama 
dan melihat token tersebut dengan perintah git log atau checkout. 
• Bahkan jika riwayat dibersihkan:  Sekali file berisi rahasia terdorong ( pushed) ke 
repositori publik atau shared, sistem harus mengasumsikan bahwa bot crawler  
penyerang sudah membaca token tersebut. 
• Prosedur Standar Industri: Jangan membuang waktu hanya dengan menghapus file 
atau mengutak -atik riwayat. Kredensial tersebut wajib langsung dianggap bocor 
(compromised) dan harus segera dirotasi (diganti dengan token baru / revoked) pada 
provider terkait.

4.  TUGAS & EVALUASI 
4.1  Pertanyaan Analisis 
Jawablah pada laporan praktikum secara argumentatif dengan merujuk pada keluaran perintah 
yang Anda peroleh sendiri. Sertakan potongan keluaran terminal sebagai bukti pendukung. 
1. Reset versus revert pada branch bersama. Seorang rekan tim melakukan commit yang 
merusak layanan pada branch main, dan commit tersebut sudah di-push serta sudah ditarik 
oleh tiga anggota lain. Ia mengusulkan git reset --hard diikuti git push --force. Jelaskan secara 
konkret kerusakan apa yang tim bul pada salinan repository ketiga rekan lainnya, lalu 
argumentasikan mengapa git revert merupakan satu-satunya pilihan yang tepat pada situasi 
ini. 
2. Peta tiga area. Berdasarkan eksperimen JOB 4, susun tabel yang memetakan kondisi 
working directory dan staging area setelah reset --soft, --mixed, dan --hard. Selanjutnya 
tentukan jenis perubahan mana yang tidak dapat dipulihkan oleh reflog, dan jelaskan 
mengapa demikian dengan merujuk pada apa saja yang sebenarnya dicatat oleh reflog. 
3. Kredensial yang terlanjur ter -commit. Sebuah token akses ter -commit pada pukul 09.00 
dan berkasnya dihapus melalui commit baru pada pukul 09.05. Jelaskan mengapa repository 
tersebut tetap harus dianggap bocor. Kemudian susun urutan tindakan penanganan yang 
benar beserta alasan mengapa urutannya tidak boleh dibalik. 
4. Ukuran commit dan kemampuan pemulihan. Tinjau riwayat commit repository Anda 
sendiri, lalu identifikasi satu commit yang sebenarnya memuat lebih dari satu perubahan logis. 
Jelaskan kesulitan konkret yang timbul apabila commit tersebut harus dibatalkan sebagian, 
dan hubungkan argumen Anda dengan  metrik Mean Time to Restore yang dibahas pada 
Minggu 1. 
5. Snapshot dan biaya branching. Dengan merujuk pada keluaran git cat -file yang Anda 
peroleh pada JOB 3, jelaskan mengapa Git disebut menyimpan snapshot alih-alih selisih, dan 
mengapa model tersebut justru tidak boros ruang penyimpanan. Selanjutnya jelaskan 
mengapa pembuatan branch pada G it hampir tidak memerlukan biaya  sebuah sifat yang 
menjadi dasar seluruh strategi branching pada Minggu 4.

4.2  Tantangan (Challenge)  bagi Mahasiswa yang Selesai Lebih Awal 
CHALLENGE: “GERBANG MUTU SEBELUM COMMIT” 
Bangun sebuah hook pre-commit pada repository praktikum Anda yang menolak commit bermasalah 
sebelum sempat masuk ke riwayat. Ketentuannya: 
1.  Berkas .git/hooks/pre -commit dibuat dapat dieksekusi dengan chmod +x, memuat set -euo 
pipefail. 
2.  Menolak commit apabila perubahan yang di -stage memuat pola yang menyerupai kredensial: 
token GitHub (ghp_), kunci akses AWS (AKIA), blok BEGIN PRIVATE KEY, atau penetapan variabel 
PASSWORD, SECRET, dan TOKEN. Gunakan git diff --cached sebagai sumber pemeriksaan, bukan 
seluruh berkas. 
3.  Menjalankan shellcheck pada setiap berkas .sh yang di -stage, dan menolak commit apabila 
terdapat peringatan. 
4.  Menolak pesan commit yang tidak mengikuti pola Conventional Commits (feat, fix, docs, chore, 
refactor, test)  gunakan hook commit-msg untuk bagian ini. 
5.  Keluar dengan exit code 1 disertai pesan galat yang jelas pada stderr, dan exit code 0 bila seluruh 
pemeriksaan lolos. 
Pengujian wajib: buktikan ketiga skenario  commit normal diterima, commit berisi string ghp_ ditolak, 
dan commit dengan skrip cacat ditolak. Lampirkan tangkapan layar ketiganya. 
Catatan: hook tidak ikut ter -push karena berada di dalam .git. Simpan salinannya pada direktori 
hooks/ di dalam repository agar dapat dibagikan kepada tim pada Minggu 4. 
Nilai tambahan: maksimal +10 poin pada nilai praktikum minggu ini.
